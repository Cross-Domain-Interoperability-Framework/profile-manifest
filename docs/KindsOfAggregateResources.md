# Different kinds of aggregate resources.
The key discriminating dimensions are:

- Do the parts have the same content type, format, and data structure? 
- Is the set of parts closed or open? 
- Are the parts independently accessible? 
- Are the parts distributed (potential under different stewardship) ? 
- Do the parts represent the same information (granularity, format, procssing level)? 


1. a Dataset that hasPart other Resources; each dataset part has one or more distributions that are WebAPI or DataDownoad.  The parts are individually accesible and might have different content types, formats, data structure, but are all related to the aggregate resource. The core data plus supporting resources that might not be data in the same sense — a codebook, a data dictionary, a quality report, a methodology document, provenance records, a thumbnail/browse image, a readme.   Includes Federated / distributed dataset in which the parts are hosted by different organizations at different URLs with potentially different access protocols, but together constitute a single logical dataset.  No single distribution gives you the whole 'Dataset'. These aren't alternative representations or parts of the same structure, they're different kinds of resources that together constitute the complete intellectual package. Examples: a federated SPARQL endpoint, a distributed STAC catalog, or a multi-node ESGF climate data archive. The RO-Crate model handles this by typing entities differently (File, CreativeWork, MediaObject) while keeping them all in hasPart.  The metadata challenge is describing the whole while the parts are independently managed and may have different availability, access policies, and update schedules.

2. A Dataset that is a collection of files with the same content type and structure .  Use glob naming, one description of datastructure. One distribution with a URL template and parameters to access items. There are two cases here: one in which the collection of files is static, the other is a dataset that grows over time by addition of new 'parts' (records, granules, files, entries...). The dataset identity is stable but its contents change. At any point in time there's a definable set of parts, but the set isn't closed. The collection is open-ended rather than a fixed set, and the parts may arrive asynchronously. The metadata challenge is describing the dataset as a whole (temporal coverage, update frequency) while the parts are still accumulating. DCAT addresses this with dcat:DatasetSeries and dcterms:accrualPeriodicity.  Examples: a set of images, all same size, with a progression of related subjects;  a series of asynchronous heliophysics burst event data;  an x-ray computed tomography dataset; a monitoring station producing daily files; a satellite mission accumulating orbit-by-orbit data; a long-running sensor network; monthly govenment employment statistics. 

3. A dataset distributed as a single file archive; one dataset, one distribution (DataDownload), parts not individually accessible on the web, but have location paths in the archive; each part can have a full description.  Parts may be homogeneous or heterogeneous.  Like OSIRIS-Rex (ada)  or NASA PDS  bundles.  Also NEXUS/hdf5 files in which there are multiple 'entry' objects that are separatly accessible datasets; the entries might have different datastructure. 

4. a dataset that has multiple distributions-- where the distributions are different representations of the same content, e.g. a geologic map spatial data set, with distribution in different formats (shapefile, geopackage...) and spatial reference systems. Tabular data distributed in Excel and CSV formats.

5. Multi-resolution / multi-scale data. The same data at multiple levels of detail/aggregation.  The parts represent the same content at different granularities, not different content. This is distinct from different formats of same content because the information content genuinely differs between levels — coarser resolution loses detail. OGC Tiles and STAC handle this with asset roles and resolution metadata. Examples: a tiled image pyramid (COG/GeoTIFF overviews, map tile sets at zoom levels); a multi-resolution climate model output, or a point cloud at different decimation levels; daily, weekly, monthly annual climate statistics.


Other situations to consider:

The distribution is a WebAPI with parameters that define the subset, and the "parts" are ephemeral query results. Subset/view-based access to a monolithic resource. A large dataset (e.g., a data cube, a relational database, an SDMX data flow) where the "parts" don't exist as pre-formed files but are generated on demand via query parameters — OPeNDAP subsetting, WCS requests, SDMX queries, SPARQL endpoints. The dataset is logically one thing with no pre-existing decomposition into parts, but access is always to a subset.  The partitioning is defined by a consumer query, not the producer; the long standing problem here is how to identify such subsets that are inputs to subsequent analysis in a manner to have an accurate provenance trace, or make the analysis reproducible.

Versioned dataset. The same dataset at different points in its revision history — not growing (#5) but replaced or corrected. Version 1.0, 1.1, 2.0, each a complete snapshot. The parts are temporal versions of the same intellectual content, related by schema:isBasedOn or DCAT versioning properties. The question is whether the versions constitute one dataset with multiple states or multiple datasets with a lineage relationship. DataCite and DCAT handle this differently — DataCite uses IsNewVersionOf/IsPreviousVersionOf relations between separate DOIs; DCAT 3 uses dcat:DatasetSeries with dcat:inSeries.

Derived/linked dataset family. A raw dataset and its processed derivatives that maintain identity relationships — raw spectra → background-corrected spectra → normalized spectra → fitted parameters. Each is a distinct dataset, but they're linked by provenance. This is different from the same content, different format situation because the information content genuinely changes at each processing step. The PROV model handles this with prov:wasDerivedFrom chains, and CDIF CreateAction provenance chain captures this pattern.
